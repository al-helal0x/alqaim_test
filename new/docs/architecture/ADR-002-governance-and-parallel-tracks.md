# ADR-002 — تصنيف القرارات الثلاثي + فتح مسارين متوازيين

> **الحالة:** ✅ معتمَد (Product/Technical Lead) — 2026-08-09
> **يبني على:** ADR-001

## القرار أ — تصنيف كل قرار/مشكلة من الآن في إحدى ثلاث طبقات

| الطبقة | التعريف | مثال |
|---|---|---|
| 🔴 **Architecture Blocking** | يؤثر على Contract أو حدود الخدمات أو Database/Event Architecture | ADR-001 بالكامل |
| 🟠 **Integration Blocking** | يمنع دمج مهمتين أو أكثر، أو يمنع تشغيل الاختبارات أصلاً | مثال جديد اكتُشف اليوم: `conftest.py` يستورد `platform_core.outbox_models` غير الموجود — **يمنع تشغيل كل اختبارات integration في المشروع** بغض النظر عن outbox |
| 🟡 **Technical Debt** | جودة كود، lint، اختبارات غير معزولة، تعليقات قديمة | 278 مخالفة ruff موروثة، تعليق `sync_manager.dart` القديم |

**قاعدة صارمة للفريق:** لا يحق لأي منفِّذ تغيير معمارية (🔴) بحجة "الكود كان يحتاج ذلك" أثناء تنفيذ مهمة من طبقة 🟠 أو 🟡 — يُرفَع كتعارض للقرار المركزي بدل حسمه فرديًا (نفس مبدأ حدود #6 الأصلي، مُعمَّم الآن على كل مهمة).

## القرار ب — عائق 🟠 جديد اكتُشف ومُعالَج فورًا (وليس ضمن أي حزمة)

أثناء تجهيز حزمتَي DI وMigration، تبيَّن أن `apps/core-api/tests/integration/conftest.py`
يحتوي `from platform_core import outbox_models` (أضافها منفِّذ سابق ضمن
دمج مهمة #12/#6 لكن دون إرفاق الملف)، وهذا **يمنع تشغيل fixture `db_session`
بالكامل** — أي كل اختبار integration في المشروع، وليس فقط ما يخص outbox.
هذا 🟠 Integration Blocking صريح يمنع حتى قبول أي عمل من الحزمتين
أدناه. **عولج فورًا**: أُضيف `platform_core/outbox_models.py` كنموذج ORM
محايد فقط (بلا أي منطق Worker/تسليم) — يكفي لفك القفل، ويبقى من اختصاص
حزمة Migration Chain استبداله بالنسخة الكاملة عند إعادة توليد السلسلة.
