## 1. لماذا تصنيف رابع منفصل؟

`ADR-002` يصنِّف كل قرار/مشكلة إلى إحدى ثلاث طبقات: 🔴 Architecture
Blocking، 🟠 Integration Blocking، 🟡 Technical Debt. هذه الطبقات الثلاث
كلها تصف **حالة الكود نفسه** (هل يعمل؟ هل يمنع الدمج؟ هل جودته منخفضة؟).

🟣 **Product Behavior Regression** يصف شيئاً مختلفاً جوهرياً: **الكود
يعمل، الاختبارات تمر، لا شيء "معطَّل" تقنياً — لكن سلوكاً تجارياً كان
معتمَداً ويعتمد عليه المستخدم النهائي اختفى بصمت** أثناء إعادة بناء أو
Refactor. لا 🔴 لأنه لا يمس Contract/حدود خدمات. لا 🠠 لأنه لا يمنع دمج أي
مهمة أخرى ولا يُسقِط أي اختبار قائم. لا 🟡 لأنه ليس دَيناً تقنياً — إنه
**فقدان قيمة تجارية فعلية للمستخدم**، وأولويته أعلى من 🟡 العادية.

**الفرق الحاسم عن الاثنين الآخرين:**

| | 🟠 Integration Blocking | 🟣 Product Behavior Regression |
|---|---|---|
| يُكتشَف بواسطة | فشل اختبار/فشل تشغيل فوري | **لا شيء يفشل تلقائياً** — يحتاج مقارنة سلوكية متعمَّدة قبل/بعد |
| متى يظهر | فوراً عند الدمج/التشغيل | قد يبقى صامتاً حتى يلاحظه مستخدم حقيقي في الإنتاج |
| مثال | `conftest.py` يستورد وحدة غير موجودة → كل الاختبارات تفشل | مسار "بيع نقدي بلا اختيار عميل" كان يعمل، اختفى بعد Refactor للـPOS، **كل الاختبارات القائمة استمرت بالنجاح لأن لا اختبار كان يغطي هذا المسار تحديداً** |

## 2. القاعدة الإلزامية

أي Refactor أو إعادة بناء لوحدة (Module) قائمة بالفعل يلتزم بهذا التسلسل،
بلا استثناء:

```
OLD MODULE
   │
   ▼
Behavior Inventory
   (قائمة صريحة مكتوبة: كل سلوك مستخدم فعلي يعتمد عليه اليوم —
    ليس "كل دالة"، بل كل سيناريو استخدام حقيقي)
   │
   ▼
لكل سلوك في القائمة، قرار صريح واحد من ثلاثة:
   ├─ Preserve              (يبقى كما هو، يُنقَل للوحدة الجديدة)
   ├─ Intentionally Change  (يتغيّر عمداً — يحتاج توثيق السبب + من وافق)
   └─ Intentionally Remove  (يُحذَف عمداً — يحتاج توثيق السبب + من وافق)
   │
   ▼
NEW MODULE
   (التنفيذ الفعلي، بعد أن كل سلوك مصنَّف صراحة أعلاه)
   │
   ▼
Regression Verification
   (E2E سلوكي — يُشغِّل السيناريو الفعلي كما يستخدمه المستخدم،
    **ليس Unit test لدالة معزولة** — Unit tests تمر رغم فقدان سلوك
    كامل لو لم تكن مصمَّمة أصلاً لتغطيته)
   │
   ▼
Approval
   (مالك المنتج/الحوكمة يوقّع على قائمة Behavior Inventory كاملة،
    ليس فقط على "الاختبارات تمر")
```

**القاعدة الصارمة:** لا يُعتبَر أي Refactor لوحدة قائمة "منتهياً" (`DONE`)
دون Behavior Inventory موقَّعة — بغض النظر عن حالة الاختبارات. "100 passed"
لا يعني "لا فقدان سلوك" إن لم تُصمَّم الاختبارات أصلاً لتغطية كل سلوك في
القائمة.
