## القرار 1 — Outbox ≠ Event Bus، وai-platform لا تستخدم outbox الخاص بـ core-api

**المبدأ:** Outbox يضمن الذرّية *داخل قاعدة بيانات الخدمة التي تملكه*. بما أن
`ai-platform` خدمة مستقلة بقاعدة بيانات مستقلة (`AI DB`، القسم 7.10 من
Blueprint)، فلا يمكنها تقنيًا ولا معماريًا الكتابة ضمن معاملة outbox
الخاصة بـ core-api. فرض توقيع `event_bus.publish(session, ...)` عليها
كان خطأً معماريًا في ملاحظة مهمة #6، وليس مجرد اختلاف تنفيذ يُحسم لاحقًا.

**البنية المعتمدة:**

```
AI Platform                              AlQaim Core (core-api)
├── AI DB                                ├── Core DB
├── AI Transaction                       ├── Core Transaction
└── AI Outbox (جديد — لم يوجد بعد)  ┐    └── Core Outbox (مهمة #6)
                                     │
                                     ▼
                              Redis / Event Bus (النقل المشترك فقط)
                                     │
                                     ▼
                          Core Event Consumer (مهمة #8)
```

**وليس** (الافتراض السابق الخاطئ):
```
AI Platform → Core API DB Outbox  ❌ (لا وصول مباشر لقاعدة بيانات لا تملكها)
```

### فصل الواجهتين رسميًا

| الواجهة | التوقيع | من يملكها |
|---|---|---|
| `Outbox.publish_in_transaction(session, event)` | يكتب الحدث ضمن نفس معاملة الخدمة المحلية، قبل commit | كل خدمة تملك outbox خاصًا بها (core-api الآن، ai-platform لاحقًا إن احتاجت ضمان عدم فقدان) |
| `EventBus.publish(event)` | نشر عبر النقل المشترك (Redis)، بلا معرفة بقاعدة بيانات أي طرف | مبدأ معماري مشترك، تنفيذ منفصل لكل خدمة خلف نفس الواجهة |

**التزام كل خدمة بنفس المبدأ المعماري وليس بنفس الكود.** `event_bus.publish(session, event_name, payload)` الحالي في core-api (مهمة #6) هو **تنفيذ Outbox الخاص بـ core-api تحديدًا**، وليس عقدًا عامًا يُفرض على أي خدمة أخرى.

**الأثر المباشر على #7:** الكود الحالي المُسلَّم (`platform_core.redis_events.publish_event` من ai-platform مباشرة إلى Redis، Fire-and-forget بلا Outbox محلي) **يبقى مقبولاً كخطوة أولى مرحليًا**، لكن **لا يُعتبر "مغلقًا نهائيًا"** — يحتاج بند respec لاحق: بناء `AI Outbox` فعلي داخل ai-platform قبل اعتماد الجسر كضامن لعدم فقدان الحدث في الإنتاج (راجع القرار 9/10 أدناه لسبب الأولوية).

## القرار 2 — معيار الحدث الموحَّد (Event Envelope)

كل حدث عبر Event Bus (بغض النظر عن الناشر) يجب أن يحمل المغلَّف التالي،
إلزاميًا من الآن فصاعدًا لأي حدث جديد أو مُعدَّل:

```
event_id          — UUID فريد لكل نشرة (وليس لكل نوع حدث)
event_name        — مثال: "InvoiceDraftReady"
aggregate_id       — معرّف الكيان المتأثر (مثال: draft_id)
occurred_at         — وقت وقوع الحدث فعليًا (ليس وقت النشر)
producer            — اسم الخدمة الناشرة ("ai-platform" | "core-api")
version              — رقم نسخة شكل الـ payload (يبدأ 1)
idempotency_key       — مفتاح تفرّد لمنع التنفيذ المزدوج (راجع القرار 4)
payload                — الحمولة التجارية كما في §2 من contracts.md
```

هذا **إضافة فوق** جدول الأحداث الحالي في `contracts.md §2`، لا يستبدله —
حقول الـ payload التجارية لكل حدث (مثل `InvoiceDraftReady`) تبقى كما هي،
لكنها الآن تُغلَّف بهذا المغلَّف الموحَّد بدل النشر الخام.

## القرار 3 — ترتيب حسم تعارض #6×#10×#11×#12 (بالأرقام الصحيحة)

```
#6  Event / Outbox Architecture + Event Envelope (القرار 1 و2 أعلاه)
      ↓
#11 Idempotency — يُعتمَد كجزء من الأساس (Foundation)، ليس ميزة معزولة
      ↓
#12 Sales Workflow — يُبنى فوق #6 (ينشر عبر المغلَّف الجديد) وفوق #11
    (استهلاكه لأي حدث وارد يجب أن يكون idempotent)
      ↓
#10 Fiscal Period — يُبنى فوق نفس الأساس؛ يحدّد a هل تُقبَل العملية أصلًا
    قبل وصولها لأي حدث
```

*(تصحيح الترقيم عن الرسالة الأصلية: الملف المتأثر بـ"Sales" هو `sales_use_cases.py` وهو تعارض #6×#11×#12 — لا #10. الملف المتأثر بـ"Fiscal Period" هو `fiscal_period_use_cases.py` وهو تعارض #6×#10. المنطق والترتيب السببي كما وصفته صحيح 100%، فقط الأرقام المطبوعة معكوسة.)*

**سبب الترتيب:** Event Bus يؤثر على الجميع → Idempotency يجب أن تكون جزءًا من معالجة أي حدث قبل أن يُبنى أي مستهلك حقيقي فوقها → Sales (#12) ينتج الأحداث فعليًا → Fiscal Period (#10) يقرر أصلًا هل تُقبل العملية.

## القرار 4 — Idempotency كجزء من الأساس

كل مستهلك حدث يجب أن يتحمّل استلام **نفس الحدث مرتين** (`idempotency_key`
متطابق) دون تنفيذ الأثر التجاري مرتين. مثال حرج (ERP):

```
InvoiceApproved #123  →  Inventory (خصم كمية)  →  Accounting (قيد)
InvoiceApproved #123  →  (تكرار)                 →  يجب ألا يتكرر الخصم/القيد
```

**الأثر التنفيذي:** أي مستهلك حدث جديد من الآن (بما فيه مستهلك #8 القادم
لـ `InvoiceDraftReady` في purchasing) يجب أن يتحقق من `idempotency_key`
قبل تنفيذ أي أثر جانبي — هذا يمتد منطق مهمة #11 (idempotency على مستوى
API request) إلى مستوى معالجة الأحداث أيضًا (مستوى مختلف من نفس المبدأ).

## القرار 5 — سياسة سلسلة Migrations

**لا حذف عشوائي.** الإجراء الإلزامي لأي فرع Alembic مكتشَف:

> **⚠️ تحديث 2026-08-09 (بعد تسليم Task #6-S2):** الرأس المذكور أدناه
> (`identity_20260808_0003`) كان صحيحًا وقت كتابة هذا القرار، لكن تجاوزه
> الزمن — أُضيفت `sales_20260809_0001` فوقه لاحقًا (دمج مهمة #11). **الرأس
> الفعلي الحالي الآن: `platform_20260809_0002`** (outbox migration، منفَّذة
> فعليًا). هذا بالضبط سبب وجود الخطوة 1 أدناه — لا تعتمد على أي رقم مكتوب،
> تحقَّق بنفسك دائمًا عبر `alembic heads` وقت التنفيذ.

```
1. تحديد الرأس الحالي الفعلي (تحقَّق بنفسك عبر `alembic heads` — لا تعتمد على أي رقم مكتوب في أي وثيقة، فالرأس يتغيّر مع كل دمج)
2. مراجعة migration المتفرعة (الآن: outbox migration الموصوفة في بطاقة
   تسليم #6 — غير موجودة كملف فعلي في الشجرة حتى الآن، فقط موصوفة)
3. إعادة توليد/تعديل الـ revision لتُبنى فوق الرأس الصحيح
4. سلسلة واحدة فقط (Single chain) — لا رأسين
5. alembic upgrade head على قاعدة بيانات حقيقية
6. اختبار Fresh DB (من الصفر)
7. اختبار Upgrade من نسخة سكيمة سابقة فعلية (وليس فقط Fresh DB)
```

**لا تُعتبر أي migration "منتهية" لمجرد وجود ملفها.**

## القرار 6 — Event Bus Singleton → Dependency Injection

مهمة مستقلة رسمية: **"Event Bus Lifecycle & Test Isolation"**. الحل
المطلوب ليس `reset_singleton()` كترقيع سريع، بل تحويل `EventBus` من
Singleton عالمي إلى Dependency Injection فعلي:

```
Application → EventBus instance → Use Cases
Test        → Fresh EventBus (بلا تسريب state بين الاختبارات)
```

**لا تُفتح كأولوية #1** — تُفتح بعد حسم القرارين 1 و3 (البلوكينغ)، ويمكن
تنفيذها بالتوازي مع القرار 5 (Migration Chain).

## القرار 9 — سيناريو AI E2E الحقيقي المستهدَف

```
AI Platform → AI Outbox → Redis → Core Event Consumer → ERP
```

السيناريو الكامل المستهدَف لمهمة #9 بعد هذا القرار (أوسع من نطاقها
الأصلي، يحتاج تحديث بطاقتها):

```
Invoice Image → AI → InvoiceDraftReady (بالمغلَّف الموحَّد، القرار 2)
→ Core Event Consumer (idempotent، القرار 4) → Draft Invoice
→ User Review → Approval → Inventory + Accounting
```

هذا أول **AI Business Flow كامل من طرف لطرف** في المشروع فعليًا.

## القرار 10 — AI Platform كـ Subsystem مستقل رسميًا في المنتج

```
                 AlQaim ERP
                      │
               API / Events (فقط)
                      │
                 AI Platform
```

**وليس** "وحدة AI داخل Core"، **ولا** "وصول مباشر لقاعدة بيانات ERP من
AI". AI Platform من الآن: Architecture + API + Data Model + Deployment
Model مستقل، لكنه جزء رسمي من منتج AlQaim. **الأثر المباشر:** مواصفة
مهمة #7 (وأي مهمة AI↔Purchasing قادمة) تحتاج تحديثًا لتعكس هذا التصور
قبل اعتمادها نهائيًا — وهذا هو سبب عدم إغلاق #7 منفردة الآن.
