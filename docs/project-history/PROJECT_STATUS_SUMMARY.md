## 1) الوضع الفعلي بجملة واحدة

دورة تجارية كاملة (بيع/شراء → مخزون → محاسبة → تقرير) **تعمل فعليًا** على
بنية Modular Monolith (FastAPI + Postgres)، مع منصة ذكاء اصطناعي مستقلة
لفهم الفواتير، وواجهة ويب، وتطبيق نقطة بيع (Flutter) يعمل Offline-first.
المشروع في **"جولة إغلاق" (Closing Sprint)** — أي تصليب وربط الأجزاء
الأخيرة، وليس بناء من الصفر.

## 3) ما تحقَّق فعليًا (وليس ادّعاءً) في آخر جولات الدمج

- ✅ **دورة كاملة end-to-end**: إنشاء فاتورة بيع → حجز مخزون → قيد محاسبي
  متوازن → ترحيل، مع idempotency (إعادة إرسال نفس الطلب لا يكرر الأثر).
- ✅ **نمط Outbox** لضمان عدم فقدان الأحداث الحرجة (`SalesInvoiceCreated`,
  `InvoicePosted`, `FiscalPeriodClosed`) حتى لو انهار التطبيق لحظة النشر.
- ✅ **عزل كامل بين اختبارات pytest** (EventBus عبر Dependency Injection
  بدل Singleton عالمي كان يسرّب حالة بين الاختبارات).
- ✅ **Migrations نظيفة على Postgres حقيقي** — رأس واحد فقط، بلا تفرّع،
  بعد إصلاح 3 أعطال حقيقية (bulk_insert تحت asyncpg، ENUM مزدوج الإنشاء،
  طول اسم migration).
- ✅ **100+ اختبار تكامل ناجح** — آخر تشغيل فعلي مُتحقَّق منه (2026-08-14،
  بعد `TASK-06-05`/CI Baseline/`TASK-AI-01`/`TASK-AI-02`): **133 passed, 4
  skipped, 0 failed** (راجع `STATUS_20_TASKS.md §18`/`§19`).
- 🟢 **`GATE-01` (Outbox) مُغلَق فعلياً** (`TASK-06-05`، §18) — لم يعد ديناً تقنياً.
- 🟢 **`TASK-AI-01` مُنجَزة بالكامل**: `POST /purchase-invoices/ai-upload`
  فعلي، من مسودة AI معتمَدة إلى فاتورة شراء مُرحَّلة، مع idempotency
  (`draft_id`) وحماية "لا إنشاء جزئي" الكاملة.
- 🟢 **`TASK-AI-02b` مُغلَقة فعلياً** (2026-08-15، `STATUS_20_TASKS.md §20`)
  — حركة مخزون لفواتير AI عبر خطوة استلام صريحة جديدة، بثلاث حراسات
  مُختبَرة (منع ازدواج مع أمر شراء، منع الاستلام قبل الترحيل، idempotency).
- 🔴 **متبقٍّ**: `TASK-AI-03` E2E الكامل (= `GATE-03`، يحتاج `ai-platform`
  حقيقي قيد التشغيل)، اختبارات Flutter فعلية (`flutter test`)، نشر فعلي
  على staging/production.

## 4) إمكانيات النظام — كمستخدم عادي (موظف مبيعات/محاسب/كاشير)

**في نقطة البيع (POS):**
- فتح جلسة بيع وإغلاقها، تسجيل مبيعات سريعة، والعمل **بدون إنترنت** ثم
  المزامنة التلقائية عند عودة الاتصال (تطبيق Flutter مستقل، شاشات فعلية:
  دخول، فتح جلسة، شاشة بيع، شاشة دفع).
- كل عملية بيع idempotent — لو تكرر إرسال نفس الطلب (انقطاع شبكة مثلاً)،
  لا يُخصَم المخزون أو يُنشأ قيد مرتين.

**في المبيعات/المشتريات:**
- عرض سعر → تحويله لأمر بيع → فاتورة، مع تتبع الحالة (مسودة → مرحّلة).
- فواتير أعلى من 10,000 تحتاج **موافقة مدير** تلقائيًا قبل الترحيل — لا
  حاجة لمتابعة يدوية خارج النظام.
- إشعارات دائن/مدين للمرتجعات.
- سندات قبض وصرف مرتبطة تلقائيًا بالفواتير المرجعية.

**في المخزون:**
- رصيد كل صنف في كل مستودع محسوب لحظيًا من حركات فعلية (وليس رقمًا يدويًا
  عرضة للخطأ)، مع تحويلات بين المستودعات وجرد للفروقات.
- تنبيه فوري (`StockLevelLow`) عند انخفاض الرصيد عن حد معيّن.

**في المحاسبة:**
- كل عملية تجارية (فاتورة، دفعة، صرف مخزون) تُولِّد قيدًا محاسبيًا متوازنًا
  تلقائيًا — لا حاجة لإدخال يدوي مزدوج.
- إقفال فترة مالية يمنع أي قيد جديد عليها تلقائيًا، وينقل صافي الربح لحساب
  الأرباح المرحّلة.

## 5) إمكانيات النظام — كمدير تنفيذي (CEO / صاحب القرار)

- **رؤية موحَّدة عبر عدة فروع ومستودعات** لنفس الشركة، مع عزل بيانات كامل
  إن كان يدير أكثر من شركة (Multi-Tenancy حقيقي من الأساس، وليس مضافًا لاحقًا).
- **تقارير مالية جاهزة عند الطلب** عبر API فعلي: ميزان المراجعة، قائمة
  الدخل، الميزانية العمومية — مبنية من القيود الفعلية، لا أرقام مؤجَّلة.
- **رقابة تلقائية على القرارات الكبيرة**: أي فاتورة بيع تتجاوز 10,000 تُحجَز
  للموافقة قبل أن تصبح ملزَمة محاسبيًا — بلا اعتماد على الانضباط اليدوي.
- **سجل تدقيق كامل** (Audit Log) يوثِّق من غيّر ماذا ومتى عبر كل الوحدات —
  مهم للمساءلة والامتثال.
- **أتمتة استخراج الفواتير الورقية عبر AI** (OCR + فهم مستندات + مطابقة
  دلالية للموردين/المنتجات) لتقليل الإدخال اليدوي — يعمل تقنيًا، بانتظار
  إغلاق نهائي قبل الاعتماد الكامل عليه في الإنتاج.
- **قابلية التوسع للمستقبل** موثَّقة ومخطَّطة (لا مرتجَلة): الموارد
  البشرية، CRM، التصنيع، BI مخصص — كلها في خارطة الطريق كمرحلة تالية بدون
  الحاجة لإعادة هيكلة الأساس الحالي.
- **لا اعتماد على مزوّد واحد للنشر**: `docker-compose.selfhosted.yml`
  متاح للنشر الذاتي، بجانب خيار السحابة.

## 6) إمكانيات النظام — كمشرف/مدير على تنفيذ المشروع تقنيًا

- **بنية معمارية صارمة ومُطبَّقة فعليًا، لا شعارًا فقط**: كل وحدة تجارية
  ملزَمة بـ4 طبقات (`domain → application → infrastructure → presentation`)
  وتُفرَض آليًا عبر Import Linter في CI — لا اتصال مباشر بقاعدة البيانات
  من أي واجهة (API-first إلزامي).
- **حوكمة قرارات موثَّقة (ADR)**: كل قرار معماري كبير (حدود AI Platform،
  Outbox ≠ EventBus، ترتيب حسم التعارضات) مسجَّل بصيغة ADR رسمية في
  `docs/architecture/` — قابل للرجوع إليه لاحقًا، وليس نقاشًا شفهيًا ضائعًا.
- **تتبّع تعارضات حقيقي بين فرق متوازية**: سجل `STATUS_20_TASKS.md` يوثِّق
  كل حالة اكتُشف فيها تعارض بين تسليمَين مستقلَّين (أشهرها هذا الدمج
  الأخير: تطبيقان متعارضان لنمط Outbox) مع القرار المتخذ وسببه — أداة
  حوكمة فعلية، لا مجرد أرشيف.
- **معايير جودة صارمة مفروضة**: ممنوع `Float` للمبالغ المالية (`Decimal`
  فقط)، ممنوع `print()` (Logger مركزي فقط)، لا ترحيل تلقائي لمخرجات AI
  بدون موافقة بشرية صريحة.
- **تحقق فعلي موثَّق لكل تسليم، لا افتراضات**: كل بند في سجل الدمج مُصنَّف
  صراحة (✅ تحقَّق فعليًا بالتشغيل / ❌ لم يُتحقَّق منه بعد) — يمنع تراكم
  "يبدو أنه يعمل" كديون تقنية خفية.
- **[محدَّث 2026-08-16] الفجوة الإدارية أعلاه مُغلَقة فعلياً منذ `§16`**:
  `AlQaim_V2_closing_sprint_plan.md` لم يُسترجَع ولم يُعَد بناؤه — بدلاً
  من ذلك حُدِّثت إحالات `README.md` الأربع لتشير إلى
  `ALQAIM_V2_MASTER_EXECUTION_PLAN.md` (موجود فعليًا في جذر المستودع)،
  وهذا هو مرجع البداية الرسمي الوحيد الآن. راجع `STATUS_20_TASKS.md §16`
  و`§21` (`PKG-D1`، أُغلِقت بلا تنفيذ لأن هذه الفقرة نفسها — قبل تحديثها
  الآن — كانت المصدر الذي بُنيت عليه مهمة `PKG-D1` خطأً).
